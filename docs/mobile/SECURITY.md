# Mobile security boundary

The default desktop opens no PAL TCP listener. Mobile access is an opt-in TLS gateway inside the existing broker; same-user Unix IPC remains separate. Pairing is locally approved: the owner shows a signed offer on the desktop and confirms the six words there. By default the phone's signed answer comes back over the network: for the five minutes a network-return offer is live, the gateway listens on the chosen addresses even with no phone paired, and before sign-in it accepts only that offer's `pair.response` (verified like a pasted answer; a second, different answer voids the offer). Offline pairing, with no listener before confirmation, remains available. Android is an untrusted remote principal even on a private LAN. There is no generic Core RPC, settings patch or graph-admin forwarding; a phone with full access reaches a shell only through the broker-owned terminal described under “Device roles” below.

A phone with limited access (the default, and every phone paired before device roles existed) has authority equal to the intersection of exact canonical project paths, pinned Ollama hosts, capabilities, ordinary desktop categories and explicitly approved saved-script IDs, and expires after 90 days unless renewed locally. The rest of this paragraph and the next describe limited phones; phones with full access follow “Device roles” below. Changing grants invalidates live sessions and command-result visibility. Native Codex execution uses restrictive policy and approval prompts. Claude execution requires a detected CLI with `--restricted`, `--strict-mcp-config`, and manual permission handling. Remote Claude ignores user/project/local settings, confines file tools to the approved working directory, and loads only the PAL MCP configuration; Bash, other code-running built-ins, and WebFetch are unavailable. Unsupported Claude versions remain read/Stop/Deny only. Native capture-sharing Allow remains unavailable without immutable media ingestion.

The desktop CLI bypass switch automatically allows CLI/provider permission requests in remote-origin sessions and delegated children only when the device has both `providers.execute` and `approvals.provider`. Questions still require answers. Device scopes, Pause, restricted native launch policy, and computer permissions remain enforced; the CLI switch does not grant additional tool categories or remove the native sandbox. Provenance is sticky; desktop involvement cannot silently upgrade those sessions. Pause, Stop, device revocation and gateway shutdown recheck/abort work at asynchronous boundaries, invalidate provider generations and close native processes. Previously completed external effects cannot be undone; an ambiguous effect is reported as unknown and is not retried.

Files are canonicalized beneath granted roots; scripts are predefined immutable executable/argv/cwd/timeout definitions reviewed by digest. Media commands retain the reviewed MPRIS target. Discovery requires the same category authority as execution. Model catalogs/defaults are withheld if their host/native execution authority is absent. No provider credentials or MCP tokens are returned to phones.

Android backup/device transfer is disabled. Private cache/media use AES-GCM with a Keystore key, and signing keys are non-exportable. Forget/revocation removes state, images and Keystore aliases. Notification content is private and lock-screen copies are redacted; tapping a request opens it in the app's Inbox, where authority-expanding actions require explicit review. Each request alerts once; a changed request alerts again. Biometric-mode devices additionally authenticate each such action; desktop-approved trusted devices sign silently with their separate non-exportable action key. Exact `sessions.send` commands are the sole proof-required exception: when welcome advertises `sendAuthentication: "connection-key"`, the background connection key signs the same challenge-bound method, parameter digest and command ID without a password or fingerprint prompt. The action key remains valid for legacy Send and mandatory for every other proof-required mutation. Its Android authentication requirement is selected by the desktop in the signed pairing offer (`actionAuthentication`); trusted mode never extends the connection key to other actions. Legacy records/offers default to biometric, and Android refuses trusted actions unless its stored policy matches the authenticated welcome. A missing welcome field means the older action-key behavior, not permission to send unsigned. No cleartext, broad storage, accessibility service, overlay or install-packages permission is requested. Markdown HTML is literal; remote images are never fetched automatically. Camera access is requested only for the pairing QR scanner or when the person chooses Camera. A full-size capture is written to a private app-cache file that the camera app receives through a non-exported FileProvider grant; it is re-encoded into the encrypted store without metadata and deleted. Shared images are imported only from `content://` URIs. Debug builds are debuggable and meant for local testing; development snapshots use the non-debuggable, R8-optimized `dev` build type. The desktop can load a phone's public pairing response from a local file; it reads at most 16 KiB and keeps only the `cere-pair://v1/` response.

The desktop gateway applies no time-based rate limits to reconnects, reads, signed actions, native-history refreshes or memory operations. It caps simultaneous sockets, pending challenges, in-flight work, authentication time, buffered output and media quotas. Incoming pre-authentication messages are rejected above 8 KiB; the WebSocket receiver still has a 1 MiB allocation ceiling shared with authenticated messages, bounded to ten sockets. This is a documented difference from the plan's proposed separate pre-auth receiver allocation cap. Memory operations are serialized per device and remote graph closures preflight a conservative whole-store budget inside the worker. Busy operations return `SESSION_BUSY`; capacity limits return `LIMIT_EXCEEDED`. Larger stores remain usable locally.

Retention: command results 30 days with persistent ID/digest tombstones; audit records 90 days; reference-only event journal 24 hours/10,000 events. Revocation purges media after owned work is stopped. Memory erasure invalidates transcripts/cache epochs and strips old command results so command recovery cannot reintroduce forgotten text. No claim is made to erase copies already sent to external providers or separately exported by the owner.

Independent implementation review found and drove fixes to signature canonicalization, post-accept uncertainty, grant-scoped command recovery, native process cancellation, media immutability/quotas, memory work budgets, cache erasure and locked-state handling. This review is not a penetration-test certification or physical-device validation. [TESTING.md](TESTING.md) records remaining release gates. Automatic certificate/key rotation is not implemented; locally reset and re-pair all devices when necessary.

Replacement offers bind the prior device ID, desktop identity, and authentication mode. Confirmation derives mode from the stored signed offer and atomically revokes the old record. Exact project IDs are reused where paths match. Endpoint renewal is local-only, requires explicit confirmation, retains TLS/signing keys, invalidates outstanding offers, and requires replacement pairing for the renewed certificate. Phone migration preserves encrypted local work and refuses unresolved operations.

Network availability is separate from authority: losing an interface removes that listener but retains the enabled preference and retries. It does not cancel accepted work. Disable, revoke, expiry, and scope changes still enforce authority independently of reachability.

Protocol 1.1 additions keep the same boundary. A hosted or compatible API turn from a phone needs `providers.api` and that provider's grant; a compatible endpoint is bound to the granted origin, and the key never leaves the desktop. Memory is reachable only through a granted memory server, for the conversation's own project; graph changes are typed, revision-bound and witnessed by the person's statement, never forwarded RPC. A phone-started capture is an image of the desktop display: it needs the capture category, is previewed as a reduced copy, and is attached only by the digest of the original the phone reviewed. Desktop draft attachments cross as name, kind, size and digest, never a path; their content is shown only on request and sent only as reviewed. Agents and approvals name agents by opaque HMAC references, not native thread IDs. The workspace card says only whether the desktop works in this project now, never window titles, commands or other paths; memory health and dependency status omit endpoints, model names and error text. Replies to phone-started turns are not read aloud on the desktop. Welcome names the exact build (version, commit, modified flag) so evidence identifies what was tested.

## Device roles (PAL Everywhere)

The desktop chooses each phone's role when pairing it, and can promote or limit it later in Settings › PAL Mobile: **observer** (read conversations, answer approvals with Deny only, read memory), **limited** (the scoped grants above) or **full access** (`owner`). A phone can lower its own role (`devices.setSelfRole`), never raise it. The role is part of the signed pairing offer; trusted-device signing never implies full access, and an existing trusted phone stays limited after upgrade.

A phone with full access has the desktop's effective authority, not a grant list: every project, provider, category and saved script, and conversations launched with the desktop's own provider policy (the CLI bypass and computer switches apply as on the desktop). It acts that way only on a connection that declares `owner.policy.v1` in `client.features`; an older app on the same device keeps limited semantics (restricted launch, Workbench takeover). Its lifetime is stored as `until-revoked`, never as an invented far-future expiry. Each phone with full access has a **working profile**: *Use my desktop choices*, *Review changes* (CLI and computer requests are asked), or *Work automatically*; a turn uses the narrower of the profile when it started and the current one. Conversations it controls return to the desktop when it is revoked or limited, and record that origin; limited provenance stays sticky as before.

Authority is still typed. Owner operations are fixed schemas mapped to named desktop services (`broker/remote/owner-schemas.ts`, `broker/remote/owner.ts`), each with a descriptor (read, mutation, signed or stream) that the gateway enforces before dispatch; mutations go through the command ledger, and signed ones need the action key exactly as before. Keys are write-only: a phone can set or clear a provider key or a tool server secret, never read one.

- **Terminal.** A PTY owned by the broker (`pal-terminal`, vendored libvterm 0.3.3, MIT) runs as the desktop account. One controller lease at a time, taken by a signed action; input carries the lease epoch and a sequence number, a repeated sequence is acknowledged without being written, and after a lost acknowledgement the phone asks `terminal.inputStatus` instead of resending. Input is never stored. Output is bounded (10,000 lines or 6 MiB of scrollback) and rendered as cells, so escape sequences cannot reach the phone's clipboard or APIs. A broker restart marks terminals interrupted. Revoking or limiting the phone ends its control and stops the terminals it started; terminals started on the desktop keep running.
- **Host commands.** A conversation's model can run a command as the desktop account only when the conversation selected the Host commands family; each command follows the working profile's CLI approval, runs in its own process group with bounded output, and an unfinished run is reported unknown after a restart.
- **Transfers.** Downloads and uploads move in 256 KiB binary frames with verified offsets; an upload installs one artifact version only after its size and SHA-256 match. Revocation purges a device's staged uploads.
- **Tool server sign-in.** OAuth for HTTP tool servers follows the MCP authorization flow through the pinned SDK (discovery, dynamic registration or an owner-entered client ID, PKCE S256, resource indicator). Tokens stay in the desktop's owner-only secrets file, are bound to the server's origin (a changed address makes them unusable) and are sent only to that origin. A phone-started sign-in returns through the app's private-use redirect `dev.otectus.cere.mobile:/oauth-callback`; the flow is bound to that phone, its state and the server definition for ten minutes, and PKCE keeps the verifier on the desktop.
- **External writes.** A call to a tool the server does not declare read-only or idempotent is recorded; when its answer is lost the outcome is unknown and an identical request is refused until a person marks the earlier one as done or not done. PAL's command IDs are not treated as exactly-once at the remote service.
- **Voice notes.** Audio is recorded only while the conversation is on screen and the microphone indicator shows; leaving the app ends the recording. The desktop transcribes it with whisper.cpp from a private temporary file that is deleted afterwards; nothing is retained. Replies read aloud use the phone's own speech engine.
- **View desktop.** Viewing starts and ends by explicit actions, and the desktop shows a notice both times. Frames are stills captured on request (grim), never a recording; input needs ydotool or wtype on the desktop and goes to the coordinates of the frame the person tapped. It never bypasses a locked session or a portal prompt, and it does not authorize a model to use the desktop.
- **Canvas previews** run in headless Chrome or Chromium against a loopback server with a per-preview token, a content security policy and host resolution that fails every name except the loopback address, so a page cannot reach the network or PAL's APIs.
- **Skills** are imported without running anything and are offered only after their version is reviewed and enabled; **specialists** have no tools and cannot approve anything; **routines** record the phone that authorized them, and revoking it pauses them until another owner resumes them.

Downgrading to a build without device roles is not supported. An older build ignores the role field and would treat a phone with full access as a limited device holding every grant (restricted launch policy, no expiry). That is less than the full role allowed, but it is untested; revoke or limit phones with full access before downgrading.
