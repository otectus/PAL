## Fixed

Ordered by severity. Item 2 is two defects (the index and the log) with one fix. Commits are on the branch; tests are named by file and title.

### 1. A forget bound to its preview could leave the record recallable after scrubbing (erasure)

- **What was wrong.** `Memory.erase` (`broker/memory.ts`) checked the preview's `expected_revision` and `selection` against the sources it had just read, scrubbed the managed conversation history and committed a retry intent, and then sent the same revision and selection to the canonical `forget`. Any commit between the two worker calls (another conversation's reply, background extraction, an expiry) failed that second check.
- **Consequence.** The inspector's **Forget**, `pal memory forget --file` with a preview, and the phone's forget and clear reported `OUTCOME_UNKNOWN`, the transcripts were already scrubbed, and the forgotten record stayed recallable and listed until the broker restarted. Ran: a scratch reproduction showed `OUTCOME_UNKNOWN`, the note still recalled, and one intent pending.
- **Fix.** The binding is still checked against the fresh sources before anything is scrubbed, where a stale preview is still refused; the canonical deletion no longer checks it again. The stored replay intent bounds a range at the moment of the request, while the live deletion keeps the request's own bounds.
- **Tests.** `tests/shared-memory.test.ts`: "a forget bound to its preview completes when other memory commits between its source lookup and the deletion" and "clearing memory removes every record it scrubbed even when the wall clock stepped back". Commits a380cf0 and 0051e5b (see [Review of this branch](#review-of-this-branch)).

### 2. The full-text index and the memory store's log kept forgotten text on disk (erasure, physical)

- **What was wrong.** Suppression cleared payloads, witnesses and retrieval documents, but FTS5 records a deleted row as a delete key and keeps its index entries until segments merge; nothing enabled FTS5's `secure-delete`. Separately, the housekeeping checkpoint is `PASSIVE`, which never shortens the write-ahead log, so earlier frames kept the pages as they were before the erasure.
- **Consequence.** The words and positions of every forgotten or expired passage stayed in `memory_fts_data`, in the database file and in every backup taken later (`VACUUM INTO` copies the index), from which the text can be reconstructed; and the text stayed in `memory.sqlite-wal` until PAL closed. Ran: after `forget`, a unique token was gone from payloads, witnesses and retrieval documents but present in the index blobs and the file; with secure-delete alone it was still in the WAL after a passive checkpoint and more writes.
- **Fix.** Migration 8 enables `secure-delete` and runs `optimize` once, which merges away what earlier erasures left. A forget, an expiry that removed anything and opening the store end with `wal_checkpoint(TRUNCATE)` (`Canonical.purgeLog`). Cost, measured on this machine's disk with a synthetic 3,000-passage store: a forget took 163–172 ms instead of 152–156 ms, and one `optimize` took 11–14 ms. SQLite warns that `optimize` can take long on a large index, so the first start after upgrading may be slower on a big store.
- **Tests.** `tests/memory-migrations.test.ts`: "S3 migration 8 removes what earlier erasures left in the full-text index, and later erasures leave nothing there" (upgrades a store written by code that knew migrations 1–7) and "a forget and an expiry leave no copy of the removed text in the write-ahead log". Migration 8's checksum is pinned. Commit 28d19a0.

### 3. The conversation database kept scrubbed passages on disk (erasure, physical)

- **What was wrong.** `Store` (`broker/store.ts`) opened `pal.sqlite` without `secure_delete`, and nothing truncated its log after an erasure's scrub.
- **Consequence.** A long message's overflow pages were freed with their text intact, and the log kept the original pages; the scrubbed text stayed readable in `pal.sqlite` even after PAL closed. Ran: a short message left nothing after a checkpoint, a long one stayed in both files.
- **Fix.** The store sets `PRAGMA secure_delete=ON`, and `Memory.erase` truncates the store's log once the scrub commits. Rewriting a 30 KB message took about 3 ms with or without it (measured on this machine's disk). Space freed by forgets before this change keeps its contents until SQLite reuses it.
- **Test.** `tests/shared-memory.test.ts`: "a scrubbed conversation passage leaves no copy in the conversation database or its log". Commit 1626da9.

### 4. A knowledge collection without cloud consent was embedded by hosted providers (cloud boundary)

- **What was wrong.** `KnowledgeCollections.run` (`broker/knowledge-collections.ts`) recorded every chunk without a sensitivity, so it was `cloud_allowed` whatever the collection's "Cloud models may read excerpts" setting said. `vectorBacklog` and `pendingArtifacts` (`canonical.ts`) select `cloud_allowed` records for a hosted provider, and a collection's scope key names the configured server.
- **Consequence.** With a hosted embedding provider selected and cloud embedding allowed, a collection the person kept from cloud models had its chunks sent to Gemini, OpenAI, Voyage or another provider. The collection page says files are indexed on this computer, and Voyage reranking of the same excerpts already required the collection's consent. Ran: the test shows the chunks queued for a hosted space before the fix. Not run: a request to a real hosted provider (no network or credentials here); the test checks the selection the embedder uses.
- **Fix.** Chunks are recorded `local_only` unless the collection allows cloud models. A consent change is recorded, then applied to the collection scope's existing records; if memory cannot apply it, the change stays recorded and the next collection operation applies it. Each collection is also brought into line once per start, which corrects collections indexed earlier. The new canonical `collection_sensitivity` accepts only a collection's scope, so it cannot widen a conversation's restricted records. An indexing job writes with the consent it started with, so a withdrawal stops a job of that collection at once (before 375aaa7 the job ran on, writing `cloud_allowed` chunks, until the changed revision failed it at commit); consent updates go one at a time and each reads the recorded consent when it is sent.
- **Tests.** `tests/knowledge-collections.test.ts`: "a collection cloud models may not read keeps its passages local, so a hosted embedding provider is never given them" and "withdrawing cloud consent while the collection is being indexed stops the indexing, so nothing it writes afterwards reaches a hosted embedding provider". AUD-013 in the same file expected the job to fail at commit with "changed in another window"; it now expects "Indexing was cancelled", and its other checks (the revision stays the withdrawal's, nothing is published, the staged generation is erased) are unchanged. Commits c089574, 5719fd7 and 375aaa7.

### 5. Pending erasures could stop memory from starting, and waited for a broker restart (erasure, availability)

- **What was wrong.** `Memory.initialize` replayed pending intents and any failure rejected `Memory.ready`. An intent whose target no longer exists fails with `NOT_FOUND` (or `UNAUTHORIZED_SCOPE` when the memory directory was replaced), every time. Intents were also replayed only at startup.
- **Consequence.** After a forget interrupted between its scrub and its deletion, followed by compaction, restoring an older store or replacing the memory directory, every memory operation failed with `NOT_FOUND` on every start. Ran: a scratch reproduction showed `ready` and `save` both failing. A forget the stopped worker never ran stayed recallable until the broker restarted.
- **Fix.** `Memory.replayPendingErasures` treats an intent whose record or scope is gone as complete; other failures still fail closed at startup. It also runs when the memory worker restarts.
- **Tests.** `tests/shared-memory.test.ts`: "an erasure interrupted after its transcripts were scrubbed is finished when memory restarts; one with nothing left to delete does not stop memory" and "a forget the stopped memory worker never ran is finished when the worker restarts" (fails on the original file). Commit a380cf0.

### 6. Failed extraction was never tried again (lost work)

- **What was wrong.** `Canonical.extractionResult` marked a failed run `retryable`, `extractionNext` claims only `pending` runs, `reconcileExtraction` skipped `retryable` ones, and the only method that requeued them (`retry`) is not exposed to any client.
- **Consequence.** Every message recorded while the extraction model was unavailable, slow or answering with invalid output was never extracted, and `health` counted its run as queued forever. Ran on the code before the fix: a failed run was never claimed again, also after the store was reopened, and stayed counted as queued.
- **Fix.** Migration 9 adds `extraction_runs.next_retry_us`. A failed run waits 30 seconds, doubling with each attempt up to six hours; after ten attempts (about four hours) it is `failed` and counted as `queues.extraction_failed`, and an extraction settings change starts it again, as it already did for runs the old route refused. Ten attempts bound what a message the model keeps answering invalidly can cost on a billed model. Reconciliation under new epochs keeps a waiting run's attempts and pause. Runs stranded before the upgrade are due at once.
- **Tests.** `tests/memory.test.ts`: "a failed extraction is tried again after a growing pause, and gives up after its attempts"; `tests/memory-migrations.test.ts`: "S3 migration 9 lets extraction that failed before the upgrade run again". Commits fed710e and 58a1c06.

### 7. A busy memory worker made recall fail instead of answering from keywords (degraded dependencies)

- **What was wrong.** `MemoryService.retrieve` (`broker/graph-memory/service.ts`) bounds its optional routes (query embedding, the vector projection, the graph) with the 500 ms retrieval deadline and runs the keyword retrieval, the authority, on the caller's own signal. The scope lookup before them also used the deadline, outside the error handling that degrades the optional routes.
- **Consequence.** Whenever the memory worker took longer than that to reach the lookup (expiry and consolidation run regardless of a turn in progress; another conversation's writes, embedding saves), the whole recall threw a `TimeoutError`: an explicit memory search by a model, the phone's search and `pal memory query` failed, and a turn's automatic recall sent nothing and marked memory degraded, although keyword recall could have answered. Ran: with the worker's answer to the lookup held past the deadline, recall threw a `TimeoutError` after about 500 ms (a scratch script, and the new test before the fix); F-004 in `tests/review-service.test.ts` failed with the same error under load in a full run.
- **Fix.** The lookup waits on the caller's signal like the keyword retrieval; the optional routes still give up at the deadline, and coverage says `deadline_partial`.
- **Test.** `tests/shared-memory.test.ts`: "a busy memory worker delays recall but does not fail it: keyword matches are still found, and coverage says the rest was cut short". Commit 86fcedf.

### 8. A message could be recorded twice after a recall timeout (data distortion)

- **What was wrong.** `Memory.prepare` and `Memory.capture` each recorded the user's message with a new random source event. When the recall deadline ended the wait after the message's write had been accepted, `capture` found no packet and wrote it again.
- **Consequence.** One statement became two sources in separate independence groups, so a claim extracted from it looked independently supported, and its candidate deadline restarted. Ran: two user observations of one message.
- **Fix.** `prepare` keeps the event before writing and `capture` reuses it; the store's duplicate check finds the first write.
- **Test.** `tests/shared-memory.test.ts`: "a message recorded after its turn stopped waiting for memory is recorded once". Commit 3845435.

### 9. A reply citing evidence it was not given lost its provenance record

- **What was wrong.** `Memory.capture` passed every `[evidence:ID]` marker in a reply as cited, and `Canonical.recordResponse` rightly refuses a record that cites evidence it was not supplied.
- **Consequence.** One invented marker, or one copied from an older reply inside a recalled passage (recalled assistant text keeps its markers), lost the turn's whole record of supplied and cited evidence and set memory to degraded with "Memory could not record this reply", although both turns had been recorded. Ran.
- **Fix.** Only citations of supplied evidence are recorded; other markers stay in the reply text. The canonical invariant is unchanged.
- **Test.** `tests/memory-recall.test.ts`: "a reply that also cites evidence it was not given is captured, and records only the citations it was supplied". Commit d0e9b28.

## Review of this branch

Rereading the diff found two flaws in my own fixes, each reproduced by a test that fails on the earlier commit and fixed in a follow-up commit, and two gaps in them, closed with tests. The final verification found a problem in the tests and, through a test that failed under load, defect 7.

- a380cf0 made the live deletion of a range erasure use the replay's `to_us`, pinned to the broker's clock. The store's commit times never go backwards, so after the wall clock stepped back they ran ahead of it, and Clear removed none of the newest records whose text it had just scrubbed. The original code was unbounded there. Fixed in 0051e5b.
- c089574 recorded applied consent as `id:allowCloud` entries in a set, so an entry for an earlier state survived; a failed withdrawal after an earlier successful one was then never retried. Fixed in 5719fd7.
- c089574 left indexing in progress on its starting consent, so a withdrawal during indexing still let the rest of that run's chunks be offered to a hosted embedder (before the fix, the new test found the chunk written after the withdrawal in both the background and the query selection). Closed in 375aaa7.
- fed710e gave up on a run after ten attempts with no way to start it again. 58a1c06 lets a settings change do so.
- Two full runs near the end each stalled in one test file, `tests/tts.test.ts` on 5719fd7 and `tests/review-core.test.ts` on 022b6f4, until I ended that file's process. The mechanism is the same in both: the test registers its temporary directory's removal before it closes the Core that lives there, hooks run in that order, and a hook that throws skips the rest (checked with a two-hook test). When the Core's memory worker was still writing as the directory went, the removal failed with `ENOTEMPTY` in `graph-memory`, `core.close()` never ran, and the orphaned worker kept the process alive (through the inspector: only stdout, stderr and the worker's message port were active, and the profile's databases were open but deleted). The pattern predates this branch; this branch makes opening a fresh store about 1 ms slower (p50 9.3 ms against 8.4 ms, two more small transactions and a checkpoint), while the machine's load average during these runs was 9 to 44, against about 2 during the first baseline run. Both files now close or clean up safely: `tts.test.ts` closes its Cores before removing the directory (022b6f4) and `review-core.test.ts` retries the removal and never throws (db5a03f), both test-only. Alone, `tts.test.ts` passed 23 of 23 six times (four before its change, two after), and `review-core.test.ts` 17 of 17 twice (before and after its change) and once on the baseline code.

## Found but not fixed

- **Free space and backups from before these fixes.** Pages freed by earlier forgets in `pal.sqlite` keep their contents until reused; a pre-migration backup keeps its copy until it expires (14 days) or is deleted, as the inspector already says. Removing them needs a `VACUUM` of the conversation database and deleting old backups, which is the owner's call. Storage-level remanence (SSD wear levelling, filesystem snapshots) is outside what SQLite can address.
- **Read-only phone turns can recall an earlier copy of their own message.** Read by tracing: a phone session without `memory.write` recalls without recording the message (`prepare` with `write=false`), so there is no observation to exclude, and an earlier copy of the same text outside the recent exchange can be recalled. The architecture document promises earlier copies are left out. A fix would pass the message's digest to `retrieve` as an exclusion. Low impact: the copy is the person's own words.
- **A replayed range erasure is bounded by the broker's clock.** Pre-existing: the stored intent's `to_us` is the broker's time of the request, so a replay after a crash misses records newer than that if the wall clock had stepped back. Using the store's latest commit time as the bound would close it.
- **Knowledge-collection chunks are archived as episodes.** Ran: `recordObservation` threads a collection source's chunks into an episode, and `maintenance` archives it after ten idle minutes, so the scope gains an extractive `episode` artifact, a second copy of the text that collection retrieval never shows (it keeps only results whose origin is a file) but that is stored and embedded. Since fix 4 it inherits the chunks' `local_only`. Erasing the source removes it with them. Skipping consolidation for document sources would remove the duplicate.
- **`Canonical.retry` is unreachable.** No client method maps to it. Since fix 6, failed extraction retries itself and a settings change restarts a run that gave up; `retry` also resets such runs, but it is still not exposed. Exposing it would be a product decision.
- **Other tests remove a live Core's directory first.** About 20 more test files register a temporary directory's removal before closing a Core inside it (`api-providers`, `audio-devices`, `browser-companion`, `compatible-auth`, `connections`, `context-plan`, `indextts`, `jobs`, `knowledge-collections`, `ollama`, `profile-packages`, `provider-bridge`, `provider-services`, `remote-rate-limits`, `remote-view`, `review-service`, `routines`, `service-manager`, `speech-cache`, `temporal-context`, `transcription`, `voice-notes`, `workspace-files`; found by a search, not each confirmed). Under heavy load any of them can stall a full run the way two did here. The fix is the same as in `tts.test.ts`: close the Core before the directory goes.
- **Expiry does not wait for a turn's recall.** A comment in `Memory.context` says housekeeping (projection, extraction, expiry) yields while a turn recalls; `MemoryService.maintain` holds back projection, extraction and review, but schedules `maintenance` (expiry and consolidation) regardless. Since defect 7 was fixed this only makes such a turn's recall later, within its eight seconds. Checking `foreground` in `scheduleRetention` would make the comment true; I left scheduling alone.
- **Tests outside memory that depend on the date or the load.** `temporal-context.test.ts` "a conversation's own zone…" (a fixture timer due on 21 November, fired by the real timer check), `provider-services.test.ts` "provider-native computer actions…" (a module-level 60-second signal) and, by reading, A01/M04 in `context-plan.test.ts` (memory still starting) fail under load or after their fixture's date; see the overall state. Fixes would give the timer a due time relative to the real clock, create the signal per test, and wait for `core.memory.ready`.
- **Dead check in `MemoryService.retrieve`.** `p.model_route === "local_only"` is never true, since routes are `local` or `cloud`. Harmless: hosted query embedding is covered by the cloud embedding consent, and local-only passages are excluded where they are selected.

## Checked and sound

Read, and where noted covered by existing or new tests that ran:

- **SQLite as the authority.** Every recall source (exact anchors, read tokens, FTS, the vector overlay, Qdrant hits, Neo4j pointers, review reordering) passes `hydrateArtifact` or `eligibleAssertion` for scope, knowledge and world time, retention, policy, erasure and sensitivity; `MemoryService.retrieve` then rechecks epochs and runs `validate_packet`. Qdrant queries also filter by owner, scope, space, generation, erasure epoch and expiry; malformed hits hydrate to nothing.
- **Scope isolation.** The key is `[ollamaHost(host), cwd]`; native providers use the configured server and Ollama conversations their saved one. `inspect`, `list`, `pins`, `releaseRetention`, `timeline`, `neighborhood`, `identity` and curation reads are scope-bound; the read-token and anchor lookups use the authorized closure.
- **Cloud and local-only boundaries.** Cloud extraction (the Ollama and API adapters check consent and the source's restriction), hosted embedding (consent, local-only excluded in all three selections, cloud-backed Ollama embedding refused), reranking (Voyage needs cloud recall, a cloud route and cloud curation consent; a model reranker runs local-only for a local route or a local-only pool), review inference (`assertTaskRouteAllowed`; the Ollama task adapter detects cloud models; unknown processing blocks dispatch), summaries, and the MCP tools, which re-check consent at call time. Memory and cloud recall start disabled.
- **Temporal logic.** Half-open intervals in `overlaps`, `remainder` and `eligibleTime`; unknown dates never get bounds; corrections need `expected_revision` and a quotation located in the source; equal-authority single-valued conflicts become disputed; identity decisions are reversible, and "not the same" blocks chains of "same".
- **Automatic recall rules.** Topic word (`recallSkip`), eight items, the BM25 floor from 50 rows, the semantic floor `max(0.4, 95th percentile)`, per-kind caps and shares, the exclusions, half weight for disputed records, omission counts, the four-turn window and its resets, and the eight-second wait with Stop (existing tests in `memory-recall.test.ts` and `shared-memory.test.ts`).
- **Trust and injection.** Packets are JSON inside delimiters whose `<pal_` and `<cere_` openings are escaped; cited evidence must have been supplied; citation hiding shares one fixture across the broker, the desktop and the phone; assistant text is labeled unverified and cannot establish an executed outcome.
- **Durability and concurrency.** WAL with FULL synchronous commits, one writer in a worker, monotonic revisions, outbox jobs in the same transaction, the watchdog's registry replay, and deletion across every projection generation before an erasure is acknowledged.
- **Migrations, retention and restore.** Checksums fail closed on an edited migration; migration 7's pin repair; the pre-migration backup; the v1 registry repair (`legacy-v1.json`); expiry, recall and forecasts all decide through `retentionDecision` → `planRetention`; restore applies the current registry to the staged copy before anything reads it.
- **Phone.** A changed transcript epoch (every erasure changes it) clears cached messages, and reads are fenced on it; erasure receipts are rechecked; inspection and erasure use the same canonical code within bounded quotas.
- **Interface.** Every memory method name the QML passes (found by searching the memory dialogs and settings for `call("…")` and `method:"…"`, 18 names) is in the broker's client allowlist.
- **Rename leftovers.** `CERE_` variables are read only as fallbacks after `PAL_` (`palEnv`, the Fish and dependency scripts); `cere-memory.fish` and `cere-memory-emitter.py` forward to the PAL files for pre-rename configurations; the `cere_` Qdrant prefix, the point-ID and task-route namespaces and the `cere-memory` Compose project are on-disk identifiers that existing installs depend on. The editor emitter, added after the rename, has no fallback because no older configuration exists. Nothing stale was found; `operations.md` now names the Fish compatibility.

Not reached in depth: the Neo4j adapter's internals (only that its pointers are rehydrated), the Hyprland, Kitty and editor collectors beyond the policy filter, the curation lease and digest flow (left to its existing tests), and the calibration and benchmark tools.
